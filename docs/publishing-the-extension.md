# Publishing the browser extensions

The Chromium and Firefox packages are built locally. Neither
package is a published store release. Use [the browser test guide](browser-testing.md)
before submitting; real-browser acceptance checks are still pending.

## Packages

```sh
npm --prefix extension run package
```

- `target/extension/mortise-extension-0.1.0.zip`: Chrome and Dia, plus compatible
  Chromium browsers. It uses a Manifest V3 service worker.
- `target/extension/mortise-extension-firefox-0.1.0.zip`: Firefox 153+, using a
  module event page and fixed ID `mortise@mortise.app`.

The package script uses an explicit runtime-file allowlist. Tests, `.env`
files, development tools and dependencies are not included. The Firefox
manifest is generated by applying `manifest.firefox.json` to the base manifest.
Both targets share the same runtime code and permissions.

## Permissions and disclosures

| Permission | Purpose |
| --- | --- |
| `nativeMessaging` | Exchange credentials and pairing messages with the local Mortise desktop app. |
| `activeTab`, `scripting` | Fill when the user requests it. |
| HTTP(S) content scripts / host permissions | Detect login forms, offer inline filling and capture submitted credentials. This is ongoing page access, not invoke-only access. |
| `webNavigation` | Check the target document and origin before filling. |
| `storage` | Retain pairing material and preferences, not a password vault. |

Firefox declares `authenticationInfo` and `websiteActivity` because the
extension passes credentials and their origins to the native app. Mozilla's
native-messaging disclosure rules apply even though this communication is
local. Do not claim "no data transmission" merely because there is no cloud
endpoint. The extension does not implement analytics or send credentials to
the account service.

References: [Mozilla native messaging](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Native_messaging),
[Firefox consent rules](https://extensionworkshop.com/documentation/develop/best-practices-for-collecting-user-data-consents/),
[background compatibility](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background).

## Before distribution

1. Complete the Chrome, Dia and Firefox manual checks, including locked vaults,
   wrong origins, password changes and restarts.
2. Prepare store accounts, a current privacy policy, screenshots and accurate
   permission explanations. Review the actual data flow for each store's form.
3. Submit Chromium to the Chrome Web Store and Firefox to AMO for signing.
   Keep the Firefox add-on ID unchanged so its native-host manifest still matches.
4. After obtaining genuine store URLs and stable IDs, replace development
   onboarding with install links and automatic registration for those IDs.
   Browser installation and Mortise pairing still require user approval.

Until Firefox signing is complete, use Load Temporary Add-on. The add-on must
be loaded again after Firefox restarts. Do not label the unsigned zip as a
normal installable release. Safari native autofill remains a later enhancement.
